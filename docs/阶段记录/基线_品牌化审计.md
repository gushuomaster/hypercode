## 分级

### A. 用户可见内容,可以较低风险进行品牌化

- 根目录文档:
  - `README.md`
  - 本地化的 `README.*.md` 文件
  - `CONTRIBUTING.md`
  - `SECURITY.md`
- 面向用户的包元数据:
  - `package.json` description
  - `sdks/vscode/package.json` 展示元数据
- CLI 界面文本:
  - `packages/opencode/src/index.ts`
  - `packages/opencode/src/temporary.ts`
  - 帮助文本、版本横幅措辞,以及错误提示文案
- 应用与桌面端 UI 文案:
  - `packages/app/src/i18n/*.ts`
  - `packages/desktop/src/renderer/i18n/*.ts`
  - `packages/opencode/src/cli/**` 中部分 TUI 组件文本
- 发布与下载文案:
  - README 安装/下载章节
  - VS Code 扩展标题与标签

### B. 技术入口点,可以更改,但需配套兼容性工作

- CLI 命令名与包 bin:
  - `packages/opencode/package.json`
  - `packages/opencode/bin/opencode`
  - 散布于 CLI 文件和测试中硬编码的 `opencode` 帮助/示例
- 配置文件名与目录:
  - `opencode.json`、`opencode.jsonc`
  - `.opencode/`
  - XDG 配置目录下的全局配置
- 环境变量:
  - `packages/core/src/flag/flag.ts` 中的 `OPENCODE_*`
  - `packages/opencode/src/effect/runtime-flags.ts`
- 缓存/数据/状态路径与安装路径:
  - `packages/core/src/global.ts`
  - 安装/卸载逻辑
- VS Code 命令 ID:
  - `opencode.openTerminal`
  - `opencode.openNewTerminal`
  - `opencode.addFilepathToTerminal`
- 测试与快照:
  - `packages/opencode/test/**`
  - `packages/app/**.test.ts*`
  - 固定了 CLI 名称或用户可见字符串的快照输出

### C. 早期阶段应保持不变或需格外谨慎处理的项

- 许可证、版权与署名:
  - `LICENSE`
  - 内嵌的第三方声明
- 上游身份与同步标记:
  - git remote 名称
  - 用于同步/发布自动化的上游仓库 URL
- 导入路径与包命名空间:
  - `@opencode-ai/*`
  - workspace 包名
  - `packages/opencode` 目录名
- 内部协议/服务标识符:
  - `@opencode/...` 服务名
  - 诸如 `opencode.*` 的遥测/日志属性键
- 兼容性敏感的配置/认证/缓存路径:
  - 现有 `.opencode` 发现逻辑
  - 现有 `OPENCODE_*` 环境变量
  - 已存储的 token 与认证内容
- 品牌资产文件名与生成产物:
  - `opencode*.svg/png/zip`
  - 锁文件与生成的 bundle

## 推荐替换清单

推荐在后续实施阶段进行:

1. 先更新根 README 品牌内容及主要的英文文档界面。
2. 将 CLI 帮助/版本展示从 `opencode`/`OpenCode` 改为 `hypercode`/`HyperCode`。
3. 新增 `hypercode` bin,同时保留 `opencode` 作为兼容别名。
4. 更新 VS Code `displayName`、description 与可见命令标题,但保持命令 ID 稳定以兼容。
5. 更新在可见 UI 中明确提及 OpenCode 的英文 app/desktop 字符串。
6. 在更改任何默认配置指引之前,先为 `HYPERCODE_*` 与新配置名添加兼容读取。

## 暂不替换

- `@opencode-ai/*` 包名
- `packages/opencode/**` 源码路径
- `LICENSE` 与署名文本
- 用于发布/同步流程的上游 GitHub URL
- 诸如 `opencode.agent.name` 的遥测键
- 在缺少回退策略时持久化的认证/token/缓存存储
- 锁文件、生成资产、快照与二进制文件,除非有意重新生成

## 风险

- 简单粗暴的替换会破坏 import、包解析、测试、插件兼容性以及上游同步工作流。
- 在没有回退的情况下更改缓存/配置/数据根目录,可能让现有用户丢失 token、本地配置、插件或会话历史。
- 重命名 VS Code 命令 ID 或包名可能破坏现有快捷方式和扩展集成。
- 过早替换 URL 或包标识符,可能在 HyperCode 基础设施就绪之前破坏安装与更新流程。
- 帮助文本的更改会波及 CLI 快照测试,必须有意识地重新生成。

## 下一阶段建议

按以下顺序推进:

1. 低风险的用户可见文本更新。
2. 双 CLI 入口支持(`hypercode` 为主,`opencode` 兼容)。
3. 为新的 `hypercode` 命名提供配置/环境变量兼容读取,并保留旧的 `opencode` 回退。
4. 添加品牌化与上游同步脚本,使未来的上游合并能够安全地重新应用品牌。

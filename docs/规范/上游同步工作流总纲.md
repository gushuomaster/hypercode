# HyperCode 上游同步工作流总纲

## 文档目的与边界

本文档定义 HyperCode 执行 upstream sync 时长期有效的工作流规则。

它负责说明：

- upstream sync 为什么必须隔离执行
- 自动化可以推进到什么程度
- 哪些情形必须停下来交给人工判断
- 应输出哪些结果、状态和报告
- 何时允许讨论正式合入

它不负责：

- 充当一次具体同步任务的执行脚本
- 固定某个时间点的目录、路径、commit、hash 或统计数字
- 代替 `docs/操作手册/上游同步操作流程.md` 中的具体执行步骤

本文档只定义工作流制度。与某次执行有关的路径、基线、变更摘要、扫描结果和取证内容，统一沉到阶段记录中保存。

## 核心原则

HyperCode 执行 upstream sync 时，长期适用以下原则：

1. 用户看到的产品必须保持为 HyperCode，而不是 opencode。
2. HyperCode 已有的品牌化、自定义功能和扩展能力不能被 upstream 同步覆盖掉。
3. upstream 更新应尽量吸收，但只允许做最小必要的兼容适配。
4. 只要无法自动判断是否保留产品能力，或者牵涉产品取舍，就必须停止并转入人工判断。
5. 不允许污染正式主线。
6. 不允许自动发布。
7. 不允许在未完成人工验收前宣称正式主线已经同步完成。

## 隔离执行原则

所有 upstream sync、merge、适配、构建、验证和报告生成产物，都必须在隔离环境中产生。

隔离执行要求：

- 必须先记录正式主线的状态。
- 必须以正式主线为起点建立隔离 worktree 或等价隔离环境。
- 必须在隔离环境中完成合并、适配、验证和报告。
- 未经过门槛检查前，不允许生成本地验收提交。
- 即使生成了本地验收提交，也不允许直接 push，更不允许直接合入正式主线。

在没有明确人工确认前，不允许执行以下正式动作：

- `git push`
- 合入正式主线
- rebase 正式主线
- `git tag`
- 自动发布
- 删除正式归档或历史分支

## 标准工作流阶段

一次 upstream sync 的标准阶段如下：

1. 读取正式主线状态。
2. 记录 upstream 变化和共同基线。
3. 创建隔离环境。
4. 合并 upstream。
5. 做最小兼容适配。
6. 执行产品化检查和工程验证。
7. 生成测试产物与影响报告。
8. 依据结果进入状态分类。
9. 通过人工验收后，再讨论正式合入准备。

自动化只能承担前期事实收集、合并试探、适配辅助、验证和报告整理。凡是涉及产品取舍、公开面判断或不可逆决策的部分，都必须保留人工裁决点。

## 影响分析口径

工作流必须区分三类变更：

- HyperCode 自定义改动
- upstream 更新
- 当前隔离测试分支中的适配改动

长期有效的判断口径是：

- 只有同时属于 HyperCode 自定义改动和 upstream 更新交集的文件，才算 upstream 真实影响到了 HyperCode 自定义区。
- 当前适配改动不能自动等同于“真实受影响文件”。
- 任何适配都必须说明它是在处理冲突、构建问题、公开面问题，还是兼容性问题。

如果工作流需要输出结论，必须明确区分：

- 未影响
- 可自动吸收
- 需要最小兼容适配
- 必须人工决策

## 自动化停止条件

出现以下情形时，自动化必须停止并转入人工判断：

- 无法判断冲突应该保留哪一侧
- 需要在产品能力之间做取舍
- 出现公开入口或产品化公开面回退
- 构建或打包失败，且无法通过最小兼容适配修复
- 需要删除 HyperCode 增强功能才能换取通过
- 存在未解决冲突

自动化停止后，输出应当是阻塞清单和当前证据，而不是继续强行推进。

## 输出物要求

一次合格的隔离同步验证，至少应输出以下类别的信息：

- 正式主线、upstream head、共同基线的记录
- 影响分析结果
- 当前适配文件说明
- 产品化公开面检查结果
- 工程验证结果
- 测试产物信息
- upstream 融入证据
- 人工验收清单
- 结论边界说明

如果需要生成报告，报告必须回答这些问题：

- upstream 是否有更新
- 是否已经在隔离环境完成合并
- 是否触及 HyperCode 自定义改动
- 是否完成最小兼容适配
- 是否生成测试产物
- 是否仍有人工决策点
- 是否可以认为正式主线已经同步

## 状态分类

最终状态只能属于以下之一：

### READY_FOR_HUMAN_VSIX

表示：

- 隔离同步已完成
- 工程验证通过
- 测试产物已生成
- 产品化公开面未发现失败
- 等待人工安装或人工验收

### NEEDS_HUMAN_DECISION

表示：

- 出现产品取舍
- 出现无法自动兼容
- 出现公开面回退
- 出现构建失败且无法自动修复

### NO_UPSTREAM_UPDATE

表示：

- upstream 没有新变化
- 无需继续同步

### SYNC_FAILED

表示：

- 合并、适配、构建、验证或报告生成失败
- 且无法通过自动化继续收敛

## 正式合入边界

只有在人工明确确认测试产物通过后，才允许进入正式合入准备。

正式合入前必须满足：

- 隔离同步验证已经完成
- 产品化公开面通过
- 工程验证通过
- 测试产物可用
- 人工验收通过
- 正式主线尚未被自动改动

正式合入准备仍然发生在独立同步分支中，而不是直接修改正式主线。

结论边界必须明确说明：

- 隔离测试版本通过，不等于正式主线已同步
- 构建通过，不等于人工验收通过
- 只有人工验收通过后，才可以讨论正式合入

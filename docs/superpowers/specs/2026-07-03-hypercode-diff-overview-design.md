# HyperCode 相对 OpenCode 的特色改动总览设计

## 目标

新增一篇长期有效的总览文档，放在 `docs/` 根目录，用于同时服务两类读者：

- 新接手维护者：快速理解 HyperCode 相对 OpenCode 的核心差异
- 现有维护者：在 upstream sync、品牌化维护和回归核对时快速定位长期应保留的特色改动

该文档回答的问题是：

- HyperCode 相比 OpenCode 做了哪些有代表性的产品化与工程化改动
- 这些改动为什么构成 HyperCode 的特色
- 这些特色大致落在哪些区域
- 维护这些特色时，应如何与现有 `规范`、`操作手册`、`阶段记录` 配合使用

## 放置位置

- 新文档路径：`docs/HyperCode 相对 OpenCode 的特色改动总览.md`

选择放在 `docs/` 根目录，而不是 `规范`、`操作手册` 或 `阶段记录`，原因是：

- 它不是规则文档，不承担长期约束定义
- 它不是操作手册，不承担执行步骤
- 它不是历史记录，不承载某次带日期的取证结果
- 它更像“长期参考总览”，与三类目录并列最清晰

## 文档边界

本文档负责：

- 提供稳定的特色改动总览
- 用产品视角解释 HyperCode 相对 OpenCode 的核心增强
- 用维护视角说明长期应关注的保留点

本文档不负责：

- 定义必须、禁止、停止条件等规范性判断
- 给出构建、同步、验收的具体命令
- 记录某次 diff、某次验证、某次阶段结论的现场证据

边界映射：

- 长期规则：`docs/规范`
- 具体执行：`docs/操作手册`
- 历史证据：`docs/阶段记录`

## 推荐结构

### 1. 文档目的与边界

简要说明本文用途、目标读者、与其他文档目录的分工。

### 2. 一页看懂的特色摘要

先用产品视角给出简短总览，控制在 5 到 8 项核心差异，便于快速浏览。

推荐纳入：

- HyperCode 品牌化公开面
- 增强版 VS Code 扩展
- `hypercode.*` 命令与配置体系
- Activity Bar / Sessions / Todo / Modified Files / Subagents / Session Panel
- workspace runtime 启动模型
- 无 license 门禁的通用版行为
- 兼容保留策略

### 3. 特色改动明细

按特色项展开，每项使用统一结构：

- 这项改动是什么
- 相比 OpenCode 增强了什么
- 主要体现在哪些区域
- 为什么它构成 HyperCode 的长期特色

这一节以“讲清楚差异”为主，不写成逐文件 diff 清单。

### 4. 维护视角的长期保留点

把特色项转译为维护语言，回答：

- 哪些公开面必须保留
- 哪些兼容项不应机械替换
- 哪些区域在 upstream sync 时最值得优先检查
- 哪些检查可以帮助确认特色是否被意外回退

这一节应与 `docs/规范/上游同步与品牌化规范.md` 保持一致，但不重复整份规范。

### 5. 如何配合现有文档使用

提供简短导航：

- 看规则：去 `docs/规范`
- 看步骤：去 `docs/操作手册`
- 看历史证据：去 `docs/阶段记录`
- 看长期特色总览：看本文

## 内容来源

本文应主要从以下现有文档抽取并稳定化表达：

- `docs/规范/上游同步与品牌化规范.md`
- `docs/阶段记录/专项_上游同步影响_20260611.md`
- `docs/阶段记录/汇报_品牌化完成.md`
- `docs/阶段记录/汇报_阶段性进展_20260616.md`

抽取原则：

- 保留长期有效的差异描述
- 删除依赖具体日期、具体 hash、具体统计数字才能成立的表述
- 避免把“某次验证时成立”的结论直接写成永远成立的事实

## 写法要求

- 前半段偏产品视角，先帮助读者建立整体认识
- 后半段偏维护视角，帮助后续长期核对
- 语言尽量稳定，不使用临时性现场措辞
- 不堆砌大段命令、hash、branch、diff 统计
- 不把文档写成规则表或验收清单

## 验收标准

完成后应满足：

- 新接手维护者能快速说清 HyperCode 相对 OpenCode 的核心特色
- 维护者能据此快速知道哪些差异值得长期保留
- 文档与 `规范 / 操作手册 / 阶段记录` 的边界清楚
- 文档内容稳定，不依赖某次历史现场才能成立

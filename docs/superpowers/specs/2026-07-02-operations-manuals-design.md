# HyperCode 操作手册优化设计

## 目标

优化 `docs/操作手册` 下的两篇文档，使其在保持现有事实边界的前提下，更适合维护者直接执行、快速阅读，并减少内容重复。

本次优化以最终可执行性为先，同时兼顾：

- 可执行性：让维护者按顺序执行时更不容易漏步骤
- 可读性：让标题层级、导航顺序、重点提示更清楚
- 去重与收口：减少两篇手册之间重复且分散的说明

## 设计结论

本次采用“中收口”方案：

- 保留 `上游同步操作流程.md` 与 `构建与交付规范.md` 两篇文档的分工
- 重写两篇文档的内部结构，使其更像可执行 SOP 和交付检查单
- 将重复内容压缩到一处，另一处只保留必要引用或结果要求
- 允许适度调整内容口径与章节顺序，以提升实用性，但不凭空新增未验证流程

## 文档分工

### 上游同步操作流程

`docs/操作手册/上游同步操作流程.md` 应成为一次 upstream sync 的主 SOP。

它负责回答：

- 我要做一次上游同步时，从哪里开始
- 按什么顺序执行
- 哪些点必须人工判断
- 做到什么结果才允许 merge-back

它应保留的核心内容：

- 前置条件
- 分支准备
- 合并 upstream
- 冲突处理原则
- rebrand 执行与停止条件
- 品牌检查
- 同步后的关键验证
- merge-back 标准
- 绝对禁止事项

它不再承担完整的交付手册职责。涉及 CLI / VSIX 构建时，应强调“需要完成的验证结果”，并在详细命令上让位于 `构建与交付规范.md`。

### 构建与交付规范

`docs/操作手册/构建与交付规范.md` 应成为独立的构建与产物验收手册。

它负责回答：

- 只想构建 CLI / VSIX 时该怎么做
- 构建前需要准备什么
- 构建后产物在哪里
- 如何做冒烟与验收
- 哪些兼容性点需要保留

它应保留的核心内容：

- 范围与产物
- 构建前提
- CLI 构建
- CLI 冒烟测试
- VSIX 依赖准备
- VSIX 打包
- VSIX 验收
- 产物清单
- 兼容性保留项
- 常见失败信号

它不再承担 upstream sync 的主流程说明。

## 结构设计

### 上游同步操作流程的推荐结构

建议将 `docs/操作手册/上游同步操作流程.md` 调整为以下结构：

1. 目标与适用范围
2. 前置条件
3. 一次同步的标准顺序
4. 冲突处理原则
5. rebrand 执行与停止条件
6. 同步后的验证
7. merge-back 标准
8. 绝对禁止事项
9. 附：高风险文件与实用检查命令

设计意图：

- 将“主线步骤”集中在中段，形成连续可执行路径
- 将补充性说明、风险提示和参考材料下沉到文末
- 让维护者优先看到“先做什么、后做什么、做到什么算通过”

### 构建与交付规范的推荐结构

建议将 `docs/操作手册/构建与交付规范.md` 调整为以下结构：

1. 目标与产物范围
2. 构建前提
3. CLI 构建
4. CLI 冒烟与通过标准
5. VSIX 依赖准备
6. VSIX 打包
7. VSIX 验收
8. 产物清单
9. 兼容性保留项
10. 常见失败信号

设计意图：

- 将“构建动作”和“验收判断”紧密配对
- 让文档能够脱离同步流程被独立使用
- 避免当前只列命令、不写成功标准的情况

## 写法规则

两篇手册统一使用更偏执行导向的写法。

推荐节奏：

- 先说明本阶段要做什么
- 再给出命令
- 再写通过标准
- 最后补充失败信号或停止条件

推荐表达方式：

- 优先使用 checklist、短段说明和命令块
- 减少大段背景性解释
- 把“必须”“不要”“只有当……才……”这类约束写成显式判断语句
- 将历史性、阶段性结论压缩为边界说明，而不是保留完整汇报口吻

## 内容删改挪规则

### 上游同步操作流程

建议保留：

- 整条同步主线
- 关键冲突规则
- rebrand 停止条件
- 品牌检查项
- merge-back 前的通过标准
- 高风险文件与实用检查命令

建议压缩：

- `项目关系` 中的背景介绍，只保留执行必需事实
- `当前已验证结论` 这类更像阶段记录的总结语气，缩成简短边界说明

建议调整位置：

- 将 `类型检查与 EXE 构建`
- 将 `VSIX 构建前置条件`
- 将 `VSIX 验证`

以上内容保留为“同步后的验证”阶段的一部分，但不再在本篇中展开成完整交付手册。

### 构建与交付规范

建议补强：

- 构建前提
- CLI / VSIX 的通过标准
- VSIX 依赖准备
- VSIX 验收
- 常见失败信号

建议保留：

- 当前范围与非范围
- 产物位置
- 兼容性保留项

建议收口：

- 把现在过短的章节改成更完整的步骤块
- 把“只列命令、不写判断标准”的段落改成“命令 + 结果判断”

## 去重策略

两篇文档采用“主流程一处、详细构建一处”的去重原则。

保留在 `上游同步操作流程.md` 的内容：

- sync 的主流程
- 品牌检查
- merge-back 所需的最终通过条件

保留在 `构建与交付规范.md` 的内容：

- `bun install`
- `bun run build --single`
- `bun run package`
- `vsce package`
- CLI 冒烟
- VSIX 打包与解包验收

处理方式：

- `上游同步操作流程.md` 在进入构建阶段时，不再完整重复命令细节
- 它只指出需要完成哪些验证，并在需要时引用 `构建与交付规范.md`
- `构建与交付规范.md` 则保留完整命令和通过标准，作为构建的唯一详细来源

## 非目标

本次优化不包含：

- 改写 `规范` 目录下的原则文档
- 新增未被验证过的工程流程
- 重做 `阶段记录` 中的历史文档
- 扩展到 `docs/README.md` 之外的全站导航体系
- 建立单独的故障排查知识库

## 实施顺序建议

建议按以下顺序执行：

1. 先重写 `上游同步操作流程.md` 的结构与主线
2. 再重写 `构建与交付规范.md` 的结构与验收逻辑
3. 最后做两篇之间的去重收口与交叉引用检查

## 验收标准

本次手册优化完成后，应满足以下结果：

- 维护者能快速看出每篇文档的职责边界
- `上游同步操作流程.md` 能顺序指导一次 sync
- `构建与交付规范.md` 能独立指导一次 CLI / VSIX 构建与验收
- 同一命令或规则不再在两篇文档中大段重复
- 两篇文档都明确写出关键通过标准与停止条件

# HyperCode docs 整理设计

## 目标

将 `docs/` 收敛为面向维护者和接手人的三类文档结构，优先服务“项目流程进展可追溯”，同时保留当前可执行文档与历史阶段结论之间的清晰边界。

## 设计结论

`docs/` 顶层目录调整为三类：

- `规范`
- `操作手册`
- `阶段记录`

其中：

- `规范` 存放长期有效的原则、边界、禁止事项和判断依据
- `操作手册` 存放当前仍可直接照做的 SOP、构建步骤和交付清单
- `阶段记录` 存放带时间背景的阶段性分析、基线审计、完成报告、影响报告和阶段汇报

## 分类规则

### 规范

满足以下任一条件的文档归入 `规范`：

- 不依赖某一个具体时间点
- 在多轮上游同步或品牌化工作中长期复用
- 用来回答“什么能做、什么不能做、为什么这样做”

当前应保留在该目录的文件：

- `上游同步工作流总纲.md`
- `上游同步与品牌化规范.md`

### 操作手册

满足以下任一条件的文档归入 `操作手册`：

- 包含明确执行步骤、命令、检查项
- 当前维护者执行任务时需要直接照做
- 更新频率跟随流程变化，而不是阶段结论变化

当前应保留在该目录的文件：

- `上游同步操作流程.md`
- `构建与交付规范.md`

### 阶段记录

满足以下任一条件的文档归入 `阶段记录`：

- 记录某个时间点的分析、结论、阶段状态或交付结果
- 用于回答“当时发生了什么、为什么这么判断、证据是什么”
- 后续可能新增同主题新文档，而不是持续覆盖原文

当前应归入该目录的文件：

- `品牌化审计基线.md`
- `品牌化完成报告.md`
- `阶段性汇报_20260616.md`
- `上游同步影响报告_20260611.md`

## 命名规则

`阶段记录` 下的文档统一使用带日期命名，强调它们是阶段性判断而不是长期规范。

推荐格式：

- `主题_YYYYMMDD.md`

适用示例：

- `阶段性汇报_20260616.md`
- `上游同步影响报告_20260611.md`
- `品牌化审计基线_20260611.md`
- `品牌化完成报告_20260616.md`

如果暂时无法确认历史准确日期，可以先保留原文件名完成目录整理，再在后续补齐日期。

## README 导航设计

`docs/README.md` 调整为三段式导航：

### 1. 先看什么

面向新接手维护者，先说明：

- 要理解长期边界，先看 `规范`
- 要执行当前工作，先看 `操作手册`
- 要追溯项目推进过程和关键结论，查看 `阶段记录`

### 2. 三类目录说明

用简短定义解释三类目录的用途：

- `规范`：长期有效的规则与边界
- `操作手册`：当前执行方法与命令
- `阶段记录`：带日期的阶段结论、进展和证据

### 3. 阅读路径

保留少量高价值入口：

- 第一次接手 upstream sync 看什么
- 执行一次 upstream sync 看什么
- 构建 CLI / VSIX 看什么
- 回溯品牌化或同步阶段进展看什么

`README` 不再逐篇详细解释所有阶段性文档，只保留分类规则与关键入口，减少后续维护负担。

## 迁移原则

- 先调整目录结构和索引，再决定是否统一重命名
- 移动文件时不改写正文结论，避免把历史记录误改成当前规范
- 若某篇文档同时具有“结论”和“规则”属性，以文档主要用途为准
- `品牌化审计基线` 视为阶段性判断，不作为长期规范保留
- `品牌化完成报告` 视为阶段性结果，不单独保留 `报告` 目录

## 非目标

本次整理不包含以下工作：

- 重写各篇文档正文
- 补充新的上游同步结论
- 建立更细的 ADR、RFC 或知识库体系
- 调整仓库根目录面向外部用户的 README 结构

## 后续执行建议

建议按以下顺序实施：

1. 新建 `阶段记录` 目录
2. 将 `报告` 与 `归档` 中文档迁入 `阶段记录`
3. 更新 `docs/README.md`
4. 删除空的 `报告`、`归档` 目录
5. 视情况统一 `阶段记录` 文件命名

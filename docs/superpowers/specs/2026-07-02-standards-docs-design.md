# HyperCode 规范文档整理设计

## 目标

整理 `docs/规范` 下的两篇规范文档，使其在不改变核心约束的前提下，同时实现：

- 边界清晰：两篇规范各自负责不同层级的规则
- 长度收口：压缩过长段落与重复叙述
- 时效降级：把带时间点、带具体基线的历史事实从规范中降级出去

## 设计结论

本次采用“中收口”方案：

- 保留 `上游同步工作流总纲.md` 与 `上游同步与品牌化规范.md` 两篇文档
- 重新定义两篇文档的职责
- 重排章节结构，使其更像长期有效的规则文档
- 把不稳定的路径、commit、hash、统计数字和历史扫描结果从“规范”中降级为“阶段记录”信息

## 文档分工

### 上游同步工作流总纲

`docs/规范/上游同步工作流总纲.md` 应成为“工作流级规范”。

它负责回答：

- 一次 upstream sync 在制度上怎么跑
- 自动化可以做到哪一步
- 哪些位置必须停下来交给人工判断
- 有哪些固定状态、固定输出和固定门槛
- 为什么不能直接污染正式主线

它应保留的核心内容：

- 工作流目标
- 核心原则
- 隔离执行原则
- 标准工作流阶段
- 影响分析口径
- 自动化停止条件
- 输出物要求
- 状态分类
- 正式合入边界

它不应继续承载过多具体环境事实，例如绝对路径、具体目录实例、某次运行时的基线变量和值。

### 上游同步与品牌化规范

`docs/规范/上游同步与品牌化规范.md` 应成为“差异维护级规范”。

它负责回答：

- HyperCode 相对 opencode 的哪些差异必须保留
- 哪些内容不允许被 upstream 恢复
- 哪些区域是高风险冲突面
- 品牌化与兼容性边界应该如何判断
- 哪些检查适合脚本做，哪些必须人工判断

它应保留的核心内容：

- 差异维护原则
- 品牌化保留规则
- 必须保留的 HyperCode 特性
- 禁止恢复项
- 高风险冲突文件或区域
- 可脚本化与人工边界
- 同步后检查类型

它不应继续承载某次基线 commit、某次 diff 统计、某次状态扫描结果等强时效信息。

## 结构设计

### 上游同步工作流总纲的推荐结构

建议将 `docs/规范/上游同步工作流总纲.md` 调整为以下结构：

1. 文档目的与边界
2. 核心原则
3. 隔离执行原则
4. 标准工作流阶段
5. 影响分析口径
6. 自动化停止条件
7. 输出物要求
8. 状态分类
9. 正式合入边界

设计意图：

- 先说明这份文档管什么、不管什么
- 再说明长期有效的流程规则
- 最后收束到输出、状态和合入边界
- 避免当前“流程 + 历史现场 + 执行剧本”混在一起

### 上游同步与品牌化规范的推荐结构

建议将 `docs/规范/上游同步与品牌化规范.md` 调整为以下结构：

1. 文档目的与边界
2. 差异维护原则
3. 必须保留的 HyperCode 特性
4. 禁止被 upstream 恢复的内容
5. 高风险冲突面
6. 品牌化与兼容性判断规则
7. 可脚本化与人工边界
8. 同步后检查项
9. 文档使用方式

设计意图：

- 让读者打开后优先看到长期有效的边界规则
- 将“判断规则”和“代表文件/代表区域”组织到一起
- 避免把历史基线、具体扫描结果和维护结论混成一篇又长又不稳定的文档

## 写法规则

两篇规范统一采用“规则优先”的写法。

推荐节奏：

- 先写文档目的和边界
- 再写规则、禁止项、只允许的判断标准
- 最后补充代表性示例或代表性文件

推荐表达方式：

- 优先使用规则块、短段说明和矩阵
- 减少大段历史叙述和执行台词
- 将“必须”“禁止”“仅允许”“出现以下情况应停止”写成显式判断语句
- 将时间敏感的事实改写成抽象规则或迁移出规范

## 删改降级规则

### 上游同步工作流总纲

建议保留：

- 自动同步目标
- 不污染正式主线的原则
- 必须在隔离环境执行的要求
- 影响分析口径
- 自动化门槛
- 报告与状态输出要求
- 人工验收与正式合入边界

建议删除或压缩：

- 任务指令式开头，例如“你现在负责执行……”
- 某次具体运行时的绝对路径
- 某次 worktree 目录格式和日期目录样例
- 某次固定变量名和具体值示例中偏临时、偏现场的信息

建议抽象保留：

- “必须记录正式主线、上游 head、共同基线”
- “必须在隔离 worktree 中执行”
- “必须在门槛满足后才允许生成本地验证提交”

### 上游同步与品牌化规范

建议保留：

- 差异维护原则
- 禁止恢复项
- 高风险冲突区域
- 品牌化和兼容性判断标准
- 可脚本化与人工处理边界
- 同步后的检查类型

建议删除或降级：

- 具体 branch 名
- 具体 commit hash
- 具体时间戳
- 某次 `BASE..HEAD` diff 数量
- 某次状态扫描结论
- 依赖某个历史提交存在与否的证明段落

建议抽象保留：

- 哪一类特性必须保留
- 哪一类公开入口不允许退回
- 哪些文件和区域一旦发生 upstream 同名修改必须人工合并

## 与阶段记录的关系

本次整理后，应明确“规范”和“阶段记录”的边界：

- 规范保存长期有效的规则、边界和判断方式
- 阶段记录保存某次扫描、某次基线、某次 diff、某次验证的事实与证据

如果某段内容必须依赖具体时间点、具体 hash、具体统计值才能成立，则默认更适合放在 `阶段记录`，而不是 `规范`。

## 非目标

本次整理不包含：

- 重写 `操作手册` 目录的内容
- 重做 `阶段记录` 文档的正文
- 建立新的 ADR / RFC 体系
- 引入新的同步策略或新的工程流程
- 补做当前仓库的历史审计数据

## 实施顺序建议

建议按以下顺序执行：

1. 先重写 `上游同步工作流总纲.md` 的职责边界与结构
2. 再重写 `上游同步与品牌化规范.md` 的职责边界与结构
3. 最后检查两篇规范与 `操作手册`、`阶段记录` 的边界是否清晰

## 验收标准

本次规范整理完成后，应满足以下结果：

- `上游同步工作流总纲.md` 清楚表达流程制度，而不是现场执行剧本
- `上游同步与品牌化规范.md` 清楚表达差异维护边界，而不是历史扫描报告
- 两篇规范的内容重复显著减少
- 明显带时间点的事实、路径和统计结果不再作为规范主体存在
- 维护者能快速区分：什么去看 `规范`，什么去看 `操作手册`，什么去看 `阶段记录`
